# 推荐流（Timeline-Recommend）设计方法论

> 本文档描述 Feed 推荐流的实现方法论。
> 推荐流的核心是「全局候选池 + 随机打散 + 时间衰减」，不需要推送。
> 不包含完整代码，只给出设计原则和算法思路。

---

## 1. 问题定义

推荐流 = 全平台未删除的帖子，按「新鲜度 + 随机性」排序，每次刷新给用户不同的内容。

目标：

- 新帖子有更多曝光机会。
- 避免时间线过于单调（纯时间倒序会让新帖霸屏）。
- 实现简单，不依赖用户关系。

---

## 2. 数据模型：全局推荐池

### 2.1 Redis ZSet：`feed:recommend`

- 类型：ZSet。
- member：`feed_id`。
- score：`rand(0, 1) × time_decay_factor`。
- 容量：10 万条。
- TTL：30 天。

### 2.2 score 计算方法论

```
time_decay_factor = 1 / (1 + hours_since_created / 24)
score = rand(0, 1) × time_decay_factor
```

效果：

- 刚发布：time_decay ≈ 1，score 接近一个随机值，有机会排到前面。
- 1 天后：time_decay ≈ 0.5，score 上限降低。
- 7 天后：time_decay ≈ 0.125，基本沉底。

### 2.3 为什么用随机 × 衰减

- 纯随机：旧帖和新帖同等曝光，新帖劣势。
- 纯时间倒序：新帖霸屏，用户刷到的内容单调。
- 随机 × 衰减：平衡新鲜度和多样性。

---

## 3. 推荐池维护

### 3.1 写入时机

帖子发布成功后，推荐池如何处理？

| 方案 | 优点 | 缺点 |
|------|------|------|
| 实时写入 | 新帖立即可见 | 写热点，大V发帖冲击推荐池 |
| 异步刷新 | 解耦，可控频率 | 新帖有延迟 |

**推荐方案：异步刷新 + 实时兜底。**

- 主逻辑：定时任务每 5 分钟从 MySQL 拉取最近合格帖子，重建推荐池。
- 实时兜底：PublishFeed 成功后异步 ZADD 一条到推荐池，但不做强依赖。

### 3.2 淘汰策略

- 超过 10 万条时，删除 score 最低的成员。
- 超过 30 天 TTL 的帖子自动过期（依赖 Redis 过期策略）。
- 帖子被删除时，从推荐池 ZREM。

### 3.3 内容过滤

推荐池只包含：

- `status = 1`（正常）。
- 非私密账号帖子（未来扩展）。
- 已过审核（未来扩展）。

过滤在写入推荐池时完成，读取时不再过滤。

## 4. 推荐流读取流程

### 4.1 无个性化版本（V1）

```
输入：page, page_size
输出：feed_id 列表

1. 从 feed:recommend 按 score 倒序取前 page_size × page 条。
2. 跳过前 (page - 1) × page_size 条。
3. 返回当前页 feed_id。
```

这是最简单的实现，所有用户看到同一推荐池。

### 4.2 简单个性化版本（V2，可选）

- 记录用户已看过的 feed_id 集合：`user:seen:{user_id}`。
- 读取推荐池时，排除已看过的 feed_id。
- 看过的集合大小限制 5000，LRU 淘汰。

### 4.3 分页方式

- V1 使用 Offset 分页。
- V2 使用 Cursor 分页（因为排除已看后 Offset 会漂移）。

---

## 5. 缓存策略

### 5.1 推荐流热点缓存

- `timeline:{user_id}:recommend` 缓存前 2 页 JSON，TTL 5 分钟。
- 为什么比关注流 TTL 长？
  - 推荐流对实时性要求略低。
  - 推荐池本身 5 分钟刷新一次。

### 5.2 帖子详情缓存

- 推荐流返回 feed_id 列表后，调用 BatchGetFeeds 获取详情。
- BatchGetFeeds 内部使用 `feed:{feed_id}` 缓存。

---

## 6. 边界场景

| 场景 | 处理 |
|------|------|
| 推荐池为空 | 降级为按 `created_at` 倒序从 MySQL 取最近帖子 |
| 返回的 feed_id 已删除 | BatchGetFeeds 过滤 status = 2，缺少数条不影响体验 |
| 高并发刷新 | 单实例定时任务 + 分布式锁（如 Redis SETNX），避免多实例同时重建 |
| 大V发帖 | 和普通用户一样进入推荐池，不按粉丝数加权 |

---

## 7. 未来扩展方向

| 方向 | 方法 |
|------|------|
| 个性化推荐 | 引入用户画像 + 协同过滤，维护多维度候选池 |
| 多池混排 | 推荐池拆为「热门池」「新帖池」「兴趣池」，按策略混排 |
| 去重 | 维护用户已曝光集合，避免重复推荐 |
| 多样性控制 | 同一作者、同一话题的帖子在相邻位置打散 |
