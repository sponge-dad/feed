# 删除评论方法论

> 本文档描述 Comment 服务「删除评论（软删除）」模块的规范与约束。
> 重点：软删除约定、权限边界、根评论 vs 子回复的 subtree 处理差异、计数回填。

---

## 1. 软删除约定

- 一律软删除：将 `status` 置为 2，**不物理删除**。
- 原因：物理删除会破坏楼中楼引用（`root_id`/`parent_id` 指向已删记录），且需保留"该评论已删除"的展示。
- 所有读查询过滤 `status = 1`，已删评论对普通用户不可见。

---

## 2. 权限校验

| 角色 | 能否删 | 错误码 |
|------|--------|--------|
| 评论作者本人 | 能 | — |
| 其他普通用户 | 否 | `CommentNoPermission=13003` |
| 管理员/运营 | 能（后续扩展） | — |

**约束**：删除前校验 `comment.user_id == 当前 user_id`（来自 metadata）。`user_id` 来源同样禁止从请求体读取。

---

## 3. 根评论删除 vs 子回复删除

视觉上楼中楼是树，存储上是两层，因此删除必须区分是否是根评论（`root_id = 0`）：

### 3.1 删除子回复（root_id != 0）

- 仅软删该单条评论。
- 其下**不会有**更深子回复需要单独处理（存储只有两层，所有"更深"回复的 `parent_id` 指向不同节点，但 `root_id` 相同且已独立存储）——它们仍可见，保持完整对话链。
- 维护根评论 `reply_count - 1`。

### 3.2 删除根评论（root_id = 0）

**决策（强制采用方案 A）**：

- **方案 A（推荐）**：仅软删根评论本身，其下所有子回复**保留**并继续可见，但根评论内容展示为「该评论已删除」，其下回复的 `reply_user_id` 引用仍有效。整体楼层不消失，对话链完整。
  - 计数：`comment_count` 减少（根 1 + 其下所有可见子回复数）；根评论 `reply_count` 不再需要（根已删）。
  - **计数口径必须全局一致（关键）**：方案 A 下删根后，其下子回复 `status` 仍为 1（仅根被软删，子回复保留以展示对话链）。因此全量重建 `comment_count`（见 `05-stats.md` / `06-cache.md`）时，不能简单 `COUNT(status=1)`，否则会把"根已删"楼内的子回复算回，与写时「减量 = 1 + 可见子回复数」口径冲突。重建口径必须是：子回复计入计数**仅当**其根评论仍 `status=1`；一级评论则自身 `status=1` 即计入。该口径同时约束 `GetCommentCount` / `BatchGetCommentCount` 的重建与列表展示，三者必须一致。
- **方案 B（不采用）**：级联软删整楼。会丢失对话上下文，且与"楼中楼保留"的产品预期冲突，故不采用。

> 采用方案 A 的理由：保留上下文、实现简单、计数可精确计算。前端对"已删除根评论"的楼层做折叠/标记展示即可。

---

## 4. 计数回填规则

定义：删除时 `comment_count:{feed_id}` 的减量 = 被删评论本身 1 + 其下可见子回复数（仅当删的是根评论时含子回复；删子回复只减 1）。

| 删除对象 | comment_count 减量 | root.reply_count 变化 |
|---------|-------------------|----------------------|
| 子回复 | 1 | 对应 root 的 reply_count - 1 |
| 根评论 | 1 + (该楼可见子回复数) | 根已删，无需维护 |

**实现约束**：
- 计算"该楼可见子回复数"用 `SELECT COUNT(*) FROM comments WHERE root_id = ? AND status = 1`（根自身除外）。此处统计的是被删根楼内自身的子回复，与全帖计数重建的"排除根已删楼"口径不冲突，二者语义统一为：**可见 = 自身 status=1 且（一级评论 或 其根评论 status=1）**。
- 子回复数 `reply_count` 维护用 `UPDATE ... reply_count = reply_count - 1 WHERE id = root_id AND status = 1`，与软删在同事务。
- 减 `comment_count` 用 `DECR`；为防止负数，DECR 前判断（见 `06-cache.md` 计数非负保护）。
- 若删的是根评论，其下子回复的 `reply_count` 都为 0，无需逐个处理。

---

## 5. comment_hot 处理

- 被删评论若已在 `comment_hot:{feed_id}` 中，用 `ZREM` 移除。
- 若删的是根评论，其下子回复是否移出 hot 由 `05-stats.md` 口径决定（建议一并移除，因整楼折叠）。

---

## 6. 幂等

- 重复删除（已 `status=2` 的评论再次删除）：直接返回成功，不重复减计数。
- 实现：删除前判断当前 `status`，已是 2 则幂等返回；或在 `UPDATE ... SET status=2 WHERE id=? AND status=1`，用受影响行数判断——受影响 0 行说明已删，幂等成功。

---

## 7. 异常场景

| 场景 | 处理原则 |
|------|---------|
| 评论不存在 | 返回 `CommentNotFound=13001` |
| 非作者删除 | 返回 `CommentNoPermission=13003` |
| DB 软删成功，Redis DECR 失败 | 返回成功，记日志；读时从 MySQL 重建计数 |
| 并发删除同一根评论 | 用 `UPDATE ... WHERE status=1` 受影响行数做最后一道幂等，避免重复减计数 |
