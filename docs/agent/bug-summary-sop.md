# Bug 总结文档编写 SOP

> 规定 AI 在「用户要求总结某个 bug」时，必须遵循的标准流程（SOP）与产出文档模板，确保排查可复现、根因可追溯、处置可落地，文档统一归档于 `docs/problem/`。

---

## 1. 适用范围

- **触发条件**：用户表达明确归档意图，例如：「总结一下这个 bug」「记录这个 bug」「把 xx 问题归档」「写个 bug 文档」。
- **不适用**：
  - 纯修复代码但未要求总结；
  - 用户只问「为什么…」而不要文档（此时按普通排查回答，不必产出文档）；
  - 临时排查调试过程（不落地为文档）。
- **产出物**：一份 bug 总结文档，默认存放于 `docs/problem/`，文件名 `YYYYMMDD-<slug>.md`（kebab-case）。

## 2. 规则（SOP 步骤）

> 以下为强制执行顺序。每条以「必须 / 禁止 / 建议」标注。

### 步骤 0：确认边界
- 必须澄清：现象、触发条件、运行环境（本地 / 生产 / 浏览器来源 Origin）、影响范围、是否已有临时排查结论。
- 禁止凭空假设根因；信息不全时先向用户确认关键点，再动手。

### 步骤 1：复现与链路梳理
- 必须画出相关调用链（如 `浏览器直传COS → gateway uploadToken → updateMe → user RPC → MySQL`），逐段标注可疑点，形成「假设清单」。
- 建议按链路从外到内（前端 → 网关 → RPC → 存储）逐段排除，避免大海捞针。

### 步骤 2：代码实证（不靠猜）
- 必须先读相关代码：涉及的 `.go`（logic/model/config）、前端 `.ts/.tsx`、`.api`、`.proto`、`.yaml`，不要直接猜根因。
- 必要时构造端到端实证验证假设：curl 调接口、临时验证程序、单元测试。
- 实证所用的临时程序 / 测试数据，验证后**必须清理**（删除临时文件、清理测试行），禁止入库、禁止遗留。
- 涉及密钥 / 凭证时，统一走 `scripts/cos-env.sh`（已被 `.gitignore` 忽略）；禁止硬编码、禁止把明文写进文档。

### 步骤 3：根因分类（必须有证据）
- 必须明确根因类别：
  - **A 类 代码缺陷**：后端 logic/model、前端逻辑错误 → 需改代码修复。
  - **B 类 配置 / 环境问题**：CORS、CAM 权限、网络、桶配置、redis/mysql 连接等 → 给出配置步骤，不改代码。
  - **C 类 混合**：代码缺陷叠加配置问题。
- 必须给出证据（实证结果 / 状态码 / 日志 / 查库结果 / diff），禁止只给结论不给证据。
- 必须区分「真 bug」与「使用方式问题」，结论需可被他人复现验证。

### 步骤 4：处置落地
- **A 类**：
  - 修复遵循 `dev-guidelines.md`；位于哪个服务改哪里（logic 只放业务、model 扩展复杂查询、common 禁止引入业务包）。
  - 涉及安全缺陷（nil panic / 路径穿越 / 注入 / 越权 / 硬编码密钥）必须显式标注并修复，并在文档中专项说明。
  - 配套补单测 / 集成测试（参考各服务 `*-test-plan.md`）。
  - 走提交规范：小步提交，`<type>(<scope>): <subject>`。
- **B 类**：给出**可执行、可勾选**的配置清单（控制台路径、字段值、生效方式、是否需重启），不改代码。
- 禁止把未经验证的「可能原因」当作结论写进文档。

### 步骤 5：产出文档
- 必须按 §3 模板写 `docs/problem/YYYYMMDD-<slug>.md`。
- 文件名示例：`20260731-avatar-upload-not-persisted.md`。
- 文档内**禁止含密钥明文**；引用代码用相对于仓库根的路径（如 `app/gateway/internal/logic/updateMeLogic.go`）。
- 产出后必须更新 `docs/problem/README.md` 文档索引。

### 步骤 6：验证与收敛
- 必须给出「如何确认已修复 / 已生效」的验证方法（前端 Network 观察、curl 复测、查库断言）。
- 必须给出回归关注点（易复发点、配置误改点、相关链路其他入口）。

## 3. Bug 总结文档模板

> 单篇 bug 文档按以下结构编写（可按实际情况裁剪，但章节顺序与标题保持一致）。

```markdown
# <Bug 标题>

> 一句话现象 + 根因。

---

## 1. 基本信息
- 编号 / 日期 / 报告人 / 状态（待修复 / 已修复 / 已配置）
- 影响范围（哪些用户 / 功能 / 环境）
- 类别：A 代码缺陷 / B 配置问题 / C 混合（对应 SOP §2 步骤 3）

## 2. 现象与复现
- 现象描述
- 触发条件 / 环境（浏览器来源 Origin、本地 / 生产）
- 复现步骤

## 3. 排查过程（时间线）
按「假设 → 验证动作 → 结果」记录，体现实证，不藏思路。

## 4. 根因
- 直接原因
- 根本原因（设计 / 约定 / 认知偏差）
- 证据（状态码、日志、查库结果、diff 行号）

## 5. 处置方案
- A 类：代码 diff 摘要（文件:行号）+ 测试补充
- B 类：配置步骤清单（可勾选）
- 安全缺陷专项说明（如涉及）

## 6. 验证与收敛
- 验证方法
- 回归关注点

## 关联文档
- [Bug 总结 SOP](../agent/bug-summary-sop.md)
- 相关设计文档（如 OSS 设计 `docs/design/oss/00-overview.md`）
- 相关代码路径（仓库根相对路径）
```

## 4. 示例（范例）

以「前端上传头像后数据库未更新」为例，其归档文档形态为：

- **现象**：浏览器改头像，保存成功提示，但 `users.avatar` 字段未变化。
- **链路**：`EditProfilePage 调 cos-js-sdk 直传 COS → 成功才 setAvatar(file_url) → 保存时 PATCH /users/me 带 avatar → gateway updateMe → user RPC UpdateUser → MySQL`。
- **实证**：注册用户 → 服务端真实 PUT 对象到 COS → 调 updateMe → 查 MySQL，`avatar` 已写入完整 URL。证明后端落库链路正常。
- **根因（B 类）**：浏览器直传被 COS 桶 CORS 拦截（`uptest` 是服务端直传不经过浏览器，故成功不代表前端成功）。直传失败 → `avatar` 保持旧值 → 保存不带头像字段 → 库不动。
- **处置**：给出控制台 CORS 配置清单（Origin 加 `http://localhost:5173` 与 `http://127.0.0.1:5173`、Methods 含 PUT、Allow-Headers `*`、Expose-Headers 含 ETag、Max-Age 600），无需改代码。
- **验证**：浏览器 F12 Network 观察 PUT 到 `*.myqcloud.com` 返回 200，且不再弹「头像上传失败」。

## 5. 检查清单

- [ ] 步骤 0：现象 / 触发条件 / 环境 / 影响范围已确认
- [ ] 步骤 1：相关调用链已画出，可疑点已列假设清单
- [ ] 步骤 2：已读相关代码；必要时已做端到端实证；临时产物已清理、未入库
- [ ] 步骤 3：根因已分类（A/B/C），且有可复现证据
- [ ] 步骤 4：处置已落地（代码修复 / 配置清单）；安全缺陷已显式修复并说明
- [ ] 步骤 5：文档已按模板产出于 `docs/problem/YYYYMMDD-<slug>.md`，无密钥明文
- [ ] 步骤 6：已给出验证方法与回归关注点
- [ ] 已更新 `docs/problem/README.md` 文档索引，相对引用无断链
