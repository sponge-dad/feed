# 文档编写规范（Document Writing Guide）

> 规定 Feed 项目 `docs/` 下所有文档（含 `agent/` 与 `design/`）的生成、修订与组织标准。AI 在新建、补充或重构任何文档前，必须先阅读本文件并遵循其约定，以保证全仓库文档结构统一、可发现、可追溯。

---

## 1. 适用范围

- **适用目录**：`docs/agent/`（AI/开发规范类）、`docs/design/`（方案与设计类）及其子目录。
- **适用动作**：新建文档、在已有文档上补充/修订、新增子目录、调整目录结构。
- **不适用**：代码文件（`.go`/`.proto`/`.api`）、仓库根 `README.md`、本仓库 `AGENTS.md`。但本规范定义的"形式标准"同样推荐用于这些文件中的文档性内容。

## 2. 分类与归属（先定位置，再写内容）

文档必须先归类，再动笔。两大维度：

| 目录 | 性质 | 内容示例 | 读者 |
|------|------|----------|------|
| `docs/agent/` | **标准（规范性）**：规定"怎么写/怎么做" | 编码规范、API 编写规范、Gateway 开发手册 | AI 与开发者（遵循） |
| `docs/design/` | **方案（描述性）**：说明"实现逻辑/技术方案" | 架构、服务设计、数据模型、API 契约、测试方案、优化记录 | AI 与开发者（参考） |

细分规则：

- 服务级设计文档放 `docs/design/<service>/`（如 `feed/`、`interaction/`、`user/`、`relation/`），统一以 `README.md` 为索引。
- 对外 API 契约放 `docs/design/api-spec/<module>.md`。
- 测试方案、优化/决策记录作为对应服务设计目录下的文档（如 `docs/design/user/test-plan.md`、`docs/design/user/bcrypt-optimization.md`）。
- 不确定归属时：纯"编写规范"归入 `agent/`，其余优先归入 `design/<service>/`。

## 3. 通用形式标准（所有文档共用）

### 3.1 文件头

每个文档以一级标题开头，紧跟一句话职责（引用块），再用 `---` 分隔：

```markdown
# 文档标题

> 一句话说明本文档的职责与适用范围。

---
```

### 3.2 编号与命名

- 同一主题下的多份文档使用两位数字前缀排序：`NN-topic.md`（`00-overview.md`、`01-architecture.md` …）。
- 目录索引文件固定命名为 `README.md`。
- 文件名用 kebab-case（小写 + 连字符），语义自解释，避免缩写歧义。

### 3.3 文件尾：关联文档

每份文档末尾必须包含 `## 关联文档` 节，用相对路径互链相关文档，形成可导航网络：

```markdown
## 关联文档

- [服务设计总览](../service-design.md)
- [API 编写规范](./api-writing-guide.md)
```

### 3.4 交叉引用

- **一律使用相对路径**（如 `./x.md`、`../design/y.md`），禁止绝对路径或仓库根路径。
- 禁止断链：新增/删除文档后，必须同步更新所有引用（含所在目录 `README.md` 与 `关联文档` 节）。
- 引用代码文件时用相对于仓库根的路径：`common/errorx/errorx.go`。

### 3.5 排版

- 标题层级从 `#` 开始递增，不跳级。
- 表格、代码块、列表按 Markdown 规范书写；代码块标注语言。
- 关键术语、文件路径、命令用行内代码 `` `...` ``。

### 3.6 目录索引

- 每个含文档的目录必须有 `README.md`，含：`## 文档索引`（表格列出本目录文件及一句话用途）、`## 阅读顺序`（可选）、`## 关联文档`。
- 新增文档后必须更新所在目录 `README.md`。

## 4. design/ 文档内容模板

用于"实现逻辑/技术方案"类文档（架构、服务设计、数据模型、测试方案、优化记录等）。必含章节（可按需裁剪，但顺序与标题保持一致）：

```markdown
# <服务/主题> 设计

> 一句话职责。

---

## 1. 概述与定位
（是什么、解决什么问题、边界）

## 2. 架构与职责
（组件/模块划分、与其他服务的关系）

## 3. 数据模型
（表/结构、字段、索引、缓存 key 约定）

## 4. 接口与契约
（对内 gRPC / 对外 REST，指向 api-spec 对应模块）

## 5. 错误码
（码段、关键错误）

## 6. 缓存与一致性
（缓存策略、读写顺序、一致性窗口）

## 7. 测试策略
（单元/集成/并发/压测要点）

## 8. 演进与 TODO
（已知缺陷、待补齐项）

## 关联文档
- ...
```

**演进式维护要求**（AI 在已有 design 文档上补充时）：

- 保留原文意图，不整体重写；以"追加小节 / 补字段 / 修正过时表述"为主。
- 内容必须与代码实现一致；发现文档与代码冲突时，以代码为准并标注待核对项，不要凭印象改写。
- 改动后更新 `关联文档` 与目录 `README.md`，并检查交叉引用无断链。

## 5. agent/ 规范文档内容模板

用于"AI/开发者遵循的规范"类文档。必含章节：

```markdown
# <主题> 编写规范

> 一句话职责。

---

## 1. 适用范围
（何时遵循本规范）

## 2. 规则
（以"必须/禁止/建议"条目化，配示例）

## 3. 示例
（正确 / 错误对照）

## 4. 检查清单
（Code Review / 提交前自检）

## 关联文档
- ...
```

## 6. AI 生成/修订文档流程

1. **先读标准**：新建或修订前先读本文件。
2. **定位置**：按 §2 归类，确定放哪个目录、文件名。
3. **套模板**：按 §4（design）或 §5（agent）组织章节。
4. **写内容**：遵循 §3 形式标准；design 类内容与代码对齐。
5. **更新索引**：补/改所在目录 `README.md` 的文档索引与阅读顺序。
6. **校验链接**：扫描相对引用，确保无断链；若属必读场景，同步登记到 `AGENTS.md` §2。
