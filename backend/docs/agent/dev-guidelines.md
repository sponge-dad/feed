# 开发规范文档

> 本文档约束 Feed 项目所有服务代码的编写方式，目的是保证团队协作时代码风格统一、
> 任何人（包括没参与设计的新同学）打开一个文件都能在 10 秒内看懂"这个文件是干什么的"。
>
> 后续所有服务（relation / feed / comment / interaction）的代码都必须遵守本规范。

---

## 1. 文件头注释规范

**每一个手写的 `.go` 文件，开头必须有文件级注释**，说明这个文件的职责。goctl/protoc
自动生成的文件（带 `Code generated by goctl/protoc. DO NOT EDIT.` 标记的）不受此约束，
不要在生成文件里手动加注释，因为下次重新生成会被覆盖。

### 1.1 模板

```go
// Package xxx 一句话说明这个包是做什么的。
//
// 更详细的说明（可选）：
//   - 这个文件/包在整个服务里承担什么角色
//   - 有什么特别需要注意的约束或坑
package xxx
```

对于不是包首个文件的普通 `.go` 文件（比如 logic 目录下每个方法一个文件），用文件级注释：

```go
// registerLogic.go
//
// 职责：处理用户注册。
// 流程：查重 -> bcrypt 加密密码 -> Snowflake 生成 ID -> 写 MySQL -> 签发 JWT。
package logic
```

### 1.2 示例（已在 common 包中落地，作为参照标准）

- `common/idgen/idgen.go` —— 包注释讲清楚了 Snowflake 位分配、用法示例
- `common/jwtx/jwtx.go` —— 包注释讲清楚了这个包在整个鉴权链路里的角色
- `common/errorx/errorx.go` —— 包注释讲清楚了错误码分段规则和用法

新写的文件请对齐这个详细程度，**不要只写一行"xxx逻辑"就完事**。

## 2. 函数/方法注释规范

- 所有 **导出的**（大写开头）函数、方法、结构体、常量，必须有注释，第一句以函数名开头
  （符合 Go 官方 `golint` 习惯），例如：

  ```go
  // Generate 为指定用户签发 token。
  func (m *Manager) Generate(userID int64, username string) (string, error) {
  ```

- logic 层的核心业务方法（如 `Register`、`Login`），除了函数签名上方的一句话说明，
  **方法体内部的每个关键步骤前都要加行内注释**，说明"这一步在做什么、为什么这么做"，
  尤其是：
  - 涉及缓存读写策略的地方（为什么先删缓存不是先写缓存）
  - 涉及批量操作代替循环单查的地方（为什么不能写 for 循环查 N 次）
  - 涉及错误码返回的地方（对应 `../design/api-spec/xxx.md` 里的哪个业务码）

### 2.1 示例

```go
// Register 处理用户注册请求。
// 流程：查重 -> 密码加密 -> 生成分布式ID -> 写库 -> 签发token。
func (l *RegisterLogic) Register(in *user.RegisterReq) (*user.RegisterResp, error) {
	// 1. 查重：用户名不允许重复注册
	_, err := l.svcCtx.UserModel.FindOneByUsername(l.ctx, in.Username)
	if err == nil {
		return nil, errorx.New(errorx.UserExists)
	}
	if !errors.Is(err, model.ErrNotFound) {
		return nil, err // 非"未找到"的错误，说明数据库异常，直接透传
	}

	// 2. bcrypt 加密密码，绝不存明文/MD5
	hashed, err := bcrypt.GenerateFromPassword([]byte(in.Password), bcrypt.DefaultCost)
	...
}
```

## 3. 目录分层职责边界

以单个 RPC 服务（如 `app/user/rpc`）为例：

| 目录/文件 | 谁写 | 职责 | 能不能改 |
|---|---|---|---|
| `xxx.proto` | 人工设计 | 定义 gRPC 契约（消息、方法） | 改了要重新 `goctl rpc protoc` |
| `xxx/xxx.pb.go`、`xxx_grpc.pb.go` | protoc 生成 | 契约的 Go 代码映射 | **禁止手动改**，改了下次生成会覆盖 |
| `internal/server/xxxServer.go` | goctl 生成 | 实现 gRPC 接口，把请求转给对应 logic | 一般不用改，除非要加公共中间件逻辑 |
| `internal/logic/xxxLogic.go` | **人工填充** | 具体业务逻辑：查库、算逻辑、返回结果 | 这是每个开发者的主要工作区 |
| `internal/svc/serviceContext.go` | **人工扩展** | 依赖注入容器：把 model/redis/jwt manager 等挂载给所有 logic 用 | 新增依赖时改这里 |
| `internal/config/config.go` | **人工扩展** | 对应 `etc/xxx.yaml` 的配置结构体 | 新增配置项时改这里 |
| `model/xxxmodel_gen.go` | goctl model 生成 | 基础 CRUD（Insert/FindOne/Update/Delete） | **禁止手动改** |
| `model/xxxmodel.go` | goctl 生成骨架 + **人工补充** | 生成时只有接口定义，自定义查询方法（如 `FindOneByUsername`）要手写补充在这里 | 可以改，这是特意留的扩展点 |
| `etc/xxx.yaml` | **人工维护** | 服务运行配置：端口、MySQL DSN、Redis 地址、密钥等 | 需要跟 config.go 字段对应 |

**核心原则**：
> 带 `DO NOT EDIT` 注释或纯粹由 `goctl`/`protoc` 生成且没有留手写扩展点的文件，永远不手动改。
> 一旦手动改了生成文件，下次重新生成代码时改动会被覆盖丢失，等于白做。

## 4. 错误处理规范

- 所有业务错误必须使用 `common/errorx` 包定义的错误码，通过 `errorx.New(code)` 返回，
  **不允许**在 logic 层用 `errors.New("用户不存在")` 这种裸字符串错误。
- 新增错误码时，去 `common/errorx/errorx.go` 里对应服务的分段（10000~10999 是 User，
  11000~11999 是 Relation……）增加常量，并同步补充 `messages` 映射表的默认提示。
- model 层查询"未找到"要用 go-zero 生成的 `model.ErrNotFound` 判断，
  不要直接判断 `err != nil` 就当成系统错误（会导致"用户不存在"被误报成"服务器内部错误"）。

## 5. 缓存操作规范（Cache-Aside）

- **读**：先查 Redis，未命中查 MySQL，查到后回写 Redis 并设置 TTL。
- **写/改**：直接更新 MySQL，然后**删除**对应缓存 key（不要直接覆盖写缓存），
  下次读取时自然触发重建，避免并发场景下写缓存脏数据。
- **批量读**：禁止在循环里逐条查 Redis/MySQL（N+1 问题），必须用 `MGET`/`IN` 批量查询。
- **例外**：超高频写场景（如点赞、收藏）允许采用「Redis 先行 + MQ 异步落库」的削峰策略，
  具体见 `docs/design/data-model.md` 第 5 节。普通业务写仍须遵循先写 DB 再删缓存。

## 6. 命名规范

- Go 文件用小驼峰命名，和 goctl 生成风格保持一致，如 `registerLogic.go`（而不是
  `register_logic.go`）。
- 结构体、导出函数用大驼峰（PascalCase）；内部变量、参数用小驼峰（camelCase）。
- Redis Key、MQ Topic 命名以 `../design/data-model.md` 和 `../design/service-design.md` 中
  已定义的为准，新增时先补充文档再写代码。

## 7. 提交前自查清单

写完一个服务的 logic 之前，过一遍这个清单：

- [ ] 每个手写文件顶部有文件级注释，说明职责
- [ ] 每个导出函数/方法有注释
- [ ] 核心业务方法内关键步骤有行内注释
- [ ] 没有手动修改任何带 `DO NOT EDIT` 标记或 `_gen.go` 后缀的生成文件
- [ ] 错误处理都走 `errorx`，没有裸 `errors.New`
- [ ] 批量场景没有写成循环单查
- [ ] `go build ./...` 编译通过
